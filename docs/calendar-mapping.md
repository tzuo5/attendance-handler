# 日历实例到定时任务的映射（P5.3）

这是设计契约和合成演练，**尚未连接真实日历，也没有把日历导入产品调度器**。使用语义见 [@tt 约定](calendar-ideation.md)，来源能力及权限见 [官方接入调研](calendar-provider-research.md)。[合成状态轨迹](examples/calendar-mapping-traces.json) 是手写的预期，不是来源响应或已经运行的同步器；P5.4 的隔离可执行样例见文末，仍仅为内存模型。

## 连接和读取契约

未来第一版建议只启用一条 Google 连接，选择少量日历，读取后识别普通文本 `@tt`，不写日历、不发送邀请。Google 只读 scopes 和 Apple 的 full access 差别沿用调研结论。Apple EventKit 留在单独验证阶段；不能同时把同一个 Google 日历的 API 与 Apple Calendar 副本当两份独立输入并承诺不会重复。

每条连接使用本机随机 UUID。断开后保留去重事实，重连必须复核账号和来源日历，继续原连接命名空间；无法证明来源相同时进入人工核对，不能自动换新 UUID 后重新启用旧事件。账号身份核实和可能需要的额外身份权限仍需真实授权阶段验证，不能声称当前研究的两个日历 scopes 已解决身份核实。换账号需要新连接，并提示可能存在复制事件；跨账号 / 跨提供者的自动合并暂不支持。

适配器提供以下经过核实的输入，映射层不直接接受任意日历文字执行指令：

| 输入 | 必须说明的含义 |
| --- | --- |
| 连接 / 日历身份 | 本机连接 UUID、来源日历 ID，是否仍在用户选择范围内 |
| 事件身份 | 普通事件 ID；重复母事件 ID、原定实例时刻及当前实例 ID 的关联；身份是否可信 |
| 时间 | 确切开始 / 结束瞬间、用于预览的城市时区或 UTC、是否全天 / 未指定结束 |
| 意图文本 | 安全转成纯文本的标题 / 描述，是否有权限读取完整识别文本 |
| 修订 | 当前已接受读取批次的版本；不能靠两个来源的更新时间大小比较先后 |
| 批次 | 完整快照或增量、覆盖范围、所有分页是否完成、权限是否有效、显式取消列表 |

初期固定一个有限的未来读取范围，例如未来 30 天，每次完整分页后才提交一批。窗口滑动后，旧窗口外的缺失项不表示删除；删除比较只作用于前后共同覆盖且确已完整读取的范围。来源失败、权限变化或部分分页不提交半批结果，暂停相关未来计划。Google 增量 `syncToken` 不能与滚动时间过滤混用；若未来改用增量，需遵守调研中的独立流程，不能把完整快照模式说成增量。

即使完整读取，共同窗口内找不到旧实例也可能是事件移出了范围。此时只停用该窗口的旧投影，保留绑定并显示“未在当前范围找到”；只有显式取消才标为来源已取消，不推断事件被删除。领取前再次取得有效完整批次，不能长期使用过期缓存自动开启；读失败沿用暂停与人工恢复规则。实际轮询间隔、请求退避和范围上限留给未来真实接入验收。

同一连接的读取串行进行；晚到旧请求、旧范围及旧授权代次的结果直接丢弃。来源变更通知仅请求再次读取，不能直接生成、删除或确认课堂。没有完整文本的私人事件先显示“无法核实日历内容”，不能把看不到 `@tt` 当移除标记。

## 事件与实例身份

身份键使用结构化数组序列化，避免用未转义的斜杠拼接来源 ID：

```text
普通事件：[connectionId, calendarId, "event", eventId]
重复实例：[connectionId, calendarId, "series", seriesId, originalStartInstant]
```

Google 重复实例使用母事件 `recurringEventId` 与原定 `originalStartTime`，不使用修改后的开始时间。普通事件的 ID-only 取消通过已保存的 event ID 别名查绑定；重复取消例外使用原定实例键。`iCalUID` 不能单独区分同系列的各次课堂。这些来源字段的依据见 [接入调研](calendar-provider-research.md)。每个重复实例展开成一个单次计划，不把任意日历 RRULE 改写成 Phase 4 的每周规则。

Apple 的外部 ID 加原定 `occurrenceDate` 只能作为核对线索，还要限定连接、来源和日历；本机 ID 在完整同步或换日历后可能变化。身份丢失 / 冲突时，暂停未来计划并请用户核对，不用标题和新开始时间自动造一个新实例。跨日历移动也不能自动重新执行；在无法可靠关联时先保留历史并阻止自动启用。Apple 的真实身份策略仍待验证。

一个实例分配一个本机 `planId`（UUID），改时、暂停、断开、取消和缓存重建都不重新生成该 ID。不同重复实例分配不同 ID。来源事件复制到另一个身份属于新草稿，仍需确认；第一版不承诺识别所有复制关系。

## 课程、时间和 Phase 4 的接口

首次只对完整课程名做精确匹配，去除首尾空白；唯一匹配也要确认绑定与启用。同名、多字段冲突或未知课程显示课程选择入口。后续使用已确认的课程 ID；本机改名不换绑。来源文字要求另一课程时暂停并重新确认，不能静默修改当前课堂。保留确认时的课程指示文本以区分“本机改名”和“来源要求换课”；来源意图含糊时保留原绑定而暂停未来计划。

时间先解析成确定的瞬间，再换算显示：带明确偏移的时间使用其瞬间；只有当地时间 + 城市时区时，夏令时缺口拒绝、回拨产生两个可能瞬间时要求补齐偏移或人工确认，不能套用 Phase 4 手填任务的“较早一次”默认。没有来源或用户明确确认的时区时不猜电脑时区。全天、`endTimeUnspecified`、不完整结束、结束不晚于开始或实际时长超出 1–720 分钟都不生成可执行计划。

现有 Phase 4 只支持整分钟开始和整数分钟时长。因此第一版拒绝带非零秒 / 毫秒或非整数分钟时长的事件并提供补齐提示，不能悄悄取整。日期也需符合现有 2000–2100 范围。

为避免同一个当地回拨时刻解析到错误瞬间，设计中的日历实例投影到 **UTC 单次任务**；另保留来源时区用于日历预览和历史展示。示例：America/Chicago 的 10 月 5 日 09:00–09:50 对应 UTC 14:00–14:50。未来产品入口应显示用户熟悉的来源时区，不能把内部 UTC 要求交给用户配置。

| Phase 4 字段 | 日历投影 |
| --- | --- |
| `id` | 既有实例的固定 `planId` |
| `courseId` | 已确认的本机课程 ID |
| `recurrence` | `{ kind: "once", date: UTC开始日期 }` |
| `localTime` / `timeZone` | UTC 开始时刻 / `UTC` |
| `durationMinutes` | `(endInstant - startInstant) / 60000`，必须为整数 |
| `enabled` | 用户明确启用，且来源健康、身份 / 课程 / 时间核实均有效、实例尚未领取 / 决定 |
| `effectiveFrom` | 首次确认、合法计划修改或人工重新启用的当前时刻 |

内容未变的重复同步不写任务、不重置 `effectiveFrom`。来源读取时间更新与任务启用时间分开。首次导入、改时或重新授权恢复时，已经过去的开始不补开；只有此前有效启用计划的 App 重启 / 唤醒，才复用 Phase 4 的十分钟宽限和原结束时间。改时更新同一单次计划，清理它的扫描进度，不能新增第二份。

### 现有调度器还缺什么

现有执行键是 `scheduleId / localDate`，它能保护同一天，但**不能单独保证日历事件移到另一日期后不重跑**。产品接入前必须增加持久的日历实例领取记录，不能只把事件转换为 `ScheduleConfig` 就宣称去重完成。

未来的同一个原子保存应同时核实当前映射版本、用户启用、来源健康和课程，并写入日历实例领取事实与 Phase 4 的执行记录，成功后才调用既有课堂启动。磁盘失败不启动；异步环境检查结束后重新核实，取消先落盘时本次不领取，领取先落盘时保留当前课堂 / 原截止并提示手动处理。当前 Store / Scheduler 尚未添加这些字段和事务。

日历实例只允许一次持久执行决定。领取、启动、失败或已落盘的跳过均保留事实；重启时不确定是否启动也进入人工恢复，不自动再试。开始后来源改时、换日期、取消或重建缓存都不会延长、换课或重新开启；本次延长仍由 App 明确操作。去重记录与最近显示的日志 / 摘要分开，不能因界面保留上限清理领取键。重连、410、课程删除和取消未来计划也不抹掉执行事实。

## 修改、错误恢复和用户选择

`userEnabled` 与 `sourceHealthy` 分开保存，避免恢复网络时自动取消用户的暂停。以下是未来预览结果，不是已添加的页面：

| 变化 | 预览与入口 | 对当前课堂的影响 |
| --- | --- | --- |
| 新事件、信息完整 | “待确认”，展示课程 / 来源时区 / 开始结束 / 运行条件 | 无；确认前不创建启用计划 |
| 合法改时且未领取 | “计划已更新”，保留计划 ID，更新生效时刻 | 无 |
| 同版本或同内容再次读取 | “同步正常”，不改变启用和生效时刻 | 无 |
| 信息不足 / 换课 / 身份不明 | “需要补齐 / 选择课程 / 核对事件”，暂停未来执行 | 原课堂保留 |
| 明确取消 / 完整文本确认移除标记 | “已取消未来计划”，保留绑定及历史；恢复事件后需重新确认启用 | 已领取实例保留原截止，提供手动结束 |
| 断网、部分分页、权限撤销 | “同步未确认 / 重新连接”，保留绑定并暂停相关未来计划 | 原课堂按自身状态恢复，不假造网站回执 |
| 410 或 EventKit 完整同步 | 重建来源缓存，保留绑定、暂停选择和领取事实 | 不重跑已决定实例 |
| App 内暂停 / 取消 | 保留用户选择；下次同步不自行启用 | 当前课堂手动决定 |
| 删除本机课程 / 断开连接 | 取消关联未来计划，清除不再需要的识别内容 / 凭据，保留最少执行事实 | 不改变已开始课堂和真实回执 |

来源恢复后，如此前确实暂停了未来执行，需用户再次启用并生成新的生效时刻；正常未中断的轮询不影响计划。断开连接应停止正在进行的来源请求，使旧响应失效；账号端撤销与只清理本机连接分别说明。Google 项目撤销、Apple 系统权限和 iCloud 账号撤销的实际范围沿用调研，不统一成一个虚假的“只撤销此日历”承诺。

## 本机最少记录和公开数据

未来本机记录按职责分开：连接 UUID / 选择范围 / 授权健康；实例身份及别名 / 最后已接受批次；确认课程和课程指示文本；固定计划 ID / 用户选择 / 暂停原因 / 来源时区及起止瞬间；独立的领取事实与原截止 / 课堂记录关联。令牌使用独立安全存储；不能写入普通 JSON 日历缓存或日志。

仅为识别短暂读取未标记文本，不持久化整份私人日历、参与者、地点或 HTML。已绑定事件只保留核对必需的内容；断开后清除文本及缓存，保留防重所需的最少身份键与执行事实。如何让用户完整删除这些本机事实及删除后无法继续保证去重，应在未来设置中明示。本轮的文件全是虚构 ID 和事件，没有保存真实日历数据。

## 合成演练与范围

[11 组状态轨迹](examples/calendar-mapping-traces.json) 各有独立初始状态，覆盖新增 / 首次确认 / 无变化同步、跨日改时、ID-only 删除、重复改时与取消例外、领取后跨日改时、分页失败 / 410 / 恢复、App 暂停、回拨第二次时刻、无明确结束 / 秒精度拒绝、Apple 身份变化及同名课程。轨迹中的任务投影用当前 Phase 4 校验器复核 UTC 起止、时长、课程引用和稳定 ID；状态变化仍是手写设计预期，不冒充同步器测试。

P5.3 的结论是：可以复用 Phase 4 的单次调度、原截止、冲突和课堂反馈；产品接入需要增加来源批次、稳定实例绑定、原子领取及来源时区展示。P5.4 在隔离样例中验证这些行为，真实 API、OAuth、EventKit 桥接和课堂执行继续保持未实现 / 待验证。

实际 [P5.4 内存原型](examples/calendar-prototype.html) 已演练六组按钮流程，验证选定的实例变更、确认、暂停与原截止模型。它没有实现完整读取窗口、HTML 转换或磁盘原子事务；这些仍是产品接入门槛，详见 [方案决策](calendar-decision.md)。
